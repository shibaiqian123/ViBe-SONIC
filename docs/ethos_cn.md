# 项目理念（ethos）

本文说明 orcs 为什么存在、它遵循哪些理念，以及代码目录如何组织。使用方法见 [readme.md](../readme.md)；本文用于理解项目的整体设计思路。

## 1. 名称

- **`orcs`**：**O**racle **R**obot **C**ontrol **S**ynthesis，可理解为“基于全知策略的机器人控制合成”。
- **oracle（全知策略）**：能够看到机器人实际无法获得的信息，例如完整仿真状态的策略。
- **synthesis（合成）**：我们先构建全知策略，再将它的能力传递给其他策略。
- **为什么叫“orc”（兽人）**：一个部落，多种躯体。各个任务是同一体系的成员，而不是独立分叉。

## 2. 核心主张：先利用特权信息，再解决部署问题

在机载传感器的限制下学习控制，实际上把两个问题混在了一起：**应该做什么**，以及**能够知道什么**。我们将它们分开解决。

```text
          完整仿真状态                          仅使用机载信息
┌──────────────────────────┐          ┌──────────────────────────┐
│ 全知策略（ORACLE POLICY） │   蒸馏   │ 学生策略（STUDENT）      │
│ 任意仿真状态             │ ───────► │ 本体感知 + 环境感知      │
│ 接触力                   │（规划中）│ 学习得到的状态估计器     │
│ 未来参考信息             │          │                          │
│ 使用特权信息的评价网络   │          │ 不保留评价网络           │
└──────────────────────────┘          └──────────────────────────┘
     训练快，但无法直接部署                 可以部署，但需要被教会
```

我们接受以下观点及其带来的设计取舍：

- **特权信息让信用分配问题更容易解决**：因此，始终先训练全知策略。
- **无法直接部署的全知策略仍值得训练**：“不能部署”不等于“没有用”。
- **感知信息的差距是一个独立的学习问题**：蒸馏是核心训练阶段，而不是事后补丁。
- **冻结一个已经具备能力的基础模型，比从零开始更好**：做适配，而不是重新训练，详见第 3 节。

## 3. 当前哪些部分使用了特权信息

我们明确说明当前状态：orcs 仍处于早期阶段。除非特别标注，以下描述均指已经实现的功能，而非未来愿景。

- **`policy`**
  - 内容：长度为 10 的本体感知历史。
  - 是否使用特权信息：否。
  - 状态：✅ 冻结的 SONIC 接口约定。

- **`tokenizer`**
  - 内容：未来参考窗口。
  - 是否使用特权信息：是，使用未来信息。
  - 状态：✅ 冻结的 SONIC 接口约定。

- **`augmentation`**
  - 内容：任务运动学信息，用作适配器的条件输入。
  - 是否使用特权信息：是，在真实硬件上需要通过感知获得。
  - 状态：✅ 已实现。

- **`critic`**
  - 内容：完整状态。
  - 是否使用特权信息：是，该网络不会部署到机器人上。
  - 状态：✅ 非对称 actor-critic。

- **学生策略**
  - 内容：通过蒸馏学习，使用本体感知和环境感知。
  - 状态：⬜ 规划中。

因此，当前使用特权信息的方式是：**非对称 actor-critic，加上任务状态真值**。例如，UOLM 使用物体状态，PerLoco 使用地形扫描，Dodge 使用球的状态。用于弥合感知差距的蒸馏阶段是下一步要实现的内容，目前尚未交付。

**做适配，而不是重新训练。** 每个任务都在已经具备控制能力、且被冻结的基础模型 SONIC WBC 上，附加一个零初始化的 LoRA 适配器。模型刚构建时，其输出与基础模型逐位一致；PPO 只更新适配器。

不要直接相信这一说法，应当实际验证：

```bash
play <task> --agent initial
```

该命令会运行刚构建的智能体，不加载任何检查点。

## 4. 分层约定

```text
src/orcs/
├── __init__.py       轻量公共 API；不会因导入而加载任务或 mjlab
├── registration.py   mjlab 入口：导入任务、接入兼容层
├── core/             不依赖具体任务的共享机器人与控制基础设施
│   ├── paths · deps · _mjlab_compat
│   │                 不包含任务语义
│   ├── data/         扫描、拼接时间线、SMPL 种子/点数据接口约定
│   ├── mdp/          命令（MultiClipMotionCommand）、观测、
│   │                 终止条件、事件
│   ├── obs.py        观测组连接逻辑，以及仅涉及机器人的观测项组合
│   ├── rl.py         PPO runner 主干，以及 actor 构建器
│   ├── registry.py   按任务注册；遇到问题时降级处理，而非抛出异常
│   └── sensors.py    机器人与地面的接触，以及触发终止的刚体命名约定
├── assets/           可复用的机器人、物体、支撑实体及场景配置
├── tasks/            每个任务对应一个可自行注册的包
│   ├── dodge/        env_cfg · observation_cfgs · mdp/
│   ├── perloco/      env_cfg · terrain · terrain_spec · sensors · sources/ · mdp/
│   │                 · roster.py + rosters/*.toml（作为包数据发布）
│   └── uolm/         env_cfg · robustness · sensors · sources/ · mdp/
└── cli/              命令行入口：数据处理流水线，位于包内部
```

以下导入规则通过代码审查和 `tests/test_registration.py` 保证：

- **`core`**
  - 可以导入：标准库、mjlab、mocke。
  - 禁止导入：`orcs.assets`、`orcs.tasks`。

- **`assets`**
  - 可以导入：`orcs.core`。
  - 禁止导入：`orcs.tasks`。

- **`tasks`**
  - 可以导入：`orcs.core`、`orcs.assets`。
  - 禁止导入：其他任务。

- **`cli`**
  - 可以导入所有层。
  - 其他层不能反过来从 `cli` 导入。

- **`registration`**
  - 可以导入所有层。
  - 它是唯一负责统一接线的地方。

- **`__init__`**
  - 可以导入标准库，并以惰性方式提供公共注册诊断信息。
  - 禁止立即导入任务或 MJLab。

**`scripts/` 不属于架构中的一个层。** 它不会随 wheel 包发布，所以放在其中的逻辑无法通过 `pip install` 后的安装包使用。可执行代码应放在 `orcs/cli/` 中，并通过 `[project.scripts]` 暴露入口。`scripts/*.py` 只保留三行包装代码，`tests/test_packaging.py` 会确保这一点。

以下两条规则具有实际价值：

1. **禁止根据 `__file__` 所在位置，通过向上跳若干层来推算路径。**

   所有路径都必须来自 `orcs.core.paths`。移动模块不应导致数据集路径悄悄失效。

2. **`core` 是不依赖具体任务的共享控制基础设施。**

   它可以了解通用的机器人形态、关节、刚体、动作片段、源数据点和参考时间线。

   但它不能了解“物体”“地形”“桌子”或“球”在某个任务中的具体含义。

   mjlab 兼容层需要任务的命令配置，因此它通过参数接收通用基类：

   ```python
   apply(multi_clip_cfgs=...)
   ```

   这部分连接在 `orcs/registration.py` 中完成。Core 永远不能向上层获取依赖。

   > **2026-08-02 修订。** 第 2 条过去写的是“零语义”。只有 core 不包含任何功能项时，这才成立；而这种情况只在项目只有一个任务时成立。
   >
   > 第二个任务 perloco 需要相同的本体感知组合、相同的 runner 主干，以及相同的 RSI、退火和冻结机制。但第 4 节又禁止它通过导入 uolm 来获取这些功能——这种约束正是在发挥预期作用。
   >
   > 因此，core 现在可以包含机器人语义，而边界也调整到了能够实际检查的位置：在 `core/` 中搜索 `"object"` 或 `"terrain"`。
   >
   > **随后，它连自己的搜索检查都没通过。** `core/sensors.py` 导出了 `terrain_contact_sensor` 和 `TERRAIN_CONTACT_SENSOR_NAME`，一共出现了 13 处匹配。规则只是看起来得到了执行。
   >
   > 因此，我们将它们改名为 `ground_contact_sensor` 和 `GROUND_CONTACT_SENSOR_NAME`。Core 只需要知道机器人站在“某个东西”上。
   >
   > `"terrain"` 在这里仅保留了一处：它作为 mjlab 的 BODY 名称，用于 `ContactMatch`。这是 mjlab 的客观接口约定，而不是我们自己的语义词汇。
   >
   > **无法执行检查的规则，只是一种偏好。** 如果下一个共享功能迫使这个词重新进入 `core/`，诚实的做法是再次修改规则，而不是偷偷绕过它。

## 5. 包的归属与安装模式

ORCS 支持同一份代码以三种模式使用。路径是一项运行时约定，不能假设代码一定运行在源码检出目录中。

- **作为依赖嵌入宿主项目**
  - 代码：`<host>/dependencies/orcs`。
  - 数据和依赖：宿主项目的 `data/` 和 `dependencies/`。

- **独立源码仓库**
  - 代码：ORCS 仓库。
  - 数据和依赖：该仓库的 `data/` 和 `dependencies/`。

- **非可编辑安装**
  - 代码：`site-packages`。
  - 数据和依赖：`$XDG_DATA_HOME/orcs/{data,dependencies}`。

可以通过 `ORCS_ROOT`、`ORCS_DATA_ROOT` 和 `ORCS_DEPS_ROOT` 覆盖这些默认路径。

单独执行 `import orcs` 是无副作用的库导入。

在 MJLab 发现和加载任务时，缺少可选数据不会导致整个包注册失败：每条任务记录要么成功注册，要么在顶层惰性加载的 `orcs.SKIP_REASON` 映射中增加一条说明。

使用方应显式检查该映射；正常的可选内容缺失不会在导入时产生警告。

## 6. 任务类别

- **`uolm`**
  - 功能：Uni-Object Loco-Manipulation，物体相关的移动操作任务。
  - 数据来源：重定向到 G1 的动作、重建的人体与物体交互动作。
  - 命令空间：`robot`、`smpl`。
  - 状态：✅ 原生训练配置和基于种子数据的 SMPL 训练配置均可训练。

- **`perloco`**
  - 功能：使用高度扫描得到的地形信息。
  - 数据来源：OmniRetarget、GRAIL。
  - 命令空间：`robot`、`smpl`（GRAIL）。
  - 状态：✅ 原生训练配置和基于种子数据的 SMPL 训练配置均可训练。

- **`dodge`**
  - 功能：全身躲球。
  - 数据来源：生成的标准站立动作。
  - 命令空间：`robot`。
  - 状态：✅ 适配器任务能够注册并训练。

- **学生策略蒸馏**
  - 功能：将全知策略转化为可部署策略。
  - 状态：⬜ 下一步要实现的内容。

## 7. 如何添加任务

1. 在 `src/orcs/tasks/<name>/__init__.py` 中构建 `_TASKS` 表，并调用：

   ```python
   orcs.core.registry.register_all(_TASKS)
   ```

   注册按记录逐条执行，因此某个数据集尚未准备好，只会影响对应的那一个任务。`SKIP_REASON[task_id]` 会说明原因。即使源码目录中没有数据，也必须能够正常导入。

2. 任务 ID 使用以下格式：

   ```text
   Orcs-<Name>-[<Source>-]<Agent>[-<CommandSpace>]
   ```

   `Agent` 始终必须显式写出，因此理解任务身份不需要事先知道默认智能体是什么。

   只有当数据来源会影响代码时，才加入 `Source` 字段，例如会改变读取器、文件格式、关节顺序或数据约定。

   perloco 的 `OmRe` 和 `Grail` 满足这一条件；路缘和楼梯地形则不满足，因此它们只是任务清单中的不同配置项，而不是不同任务。

3. 在 `src/orcs/registration.py` 中添加一行：

   ```python
   import orcs.tasks.<name>
   ```

4. 从 `orcs.assets` 获取机器人和物体资源，从 `orcs.core.paths` 获取路径。如果需要新的机器人，添加 `orcs/assets/<robot>.py`，并将其重新导出。

5. 当某项功能需要被第二个任务共用时，将它下移一层——**但必须等第二个任务真正出现之后再做。** 不做推测性的抽象。

6. 任务运行时需要的非 `.py` 文件，例如任务清单或数据结构定义，必须加入 `[tool.setuptools.package-data]`；否则它们只存在于源码目录中，不会随安装包发布。
